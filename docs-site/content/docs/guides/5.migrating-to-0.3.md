# Migrating to 0.3

`0.3` keeps the existing middleware classes and environment variables. The
default provider is `auth-service`, so an existing auth-service deployment works
after the dependency upgrade. The following behaviours are now explicit.

## Machine tokens

Native `client_credentials` tokens (`sub === azp`) are refused by default with
`ERR_MACHINE_TOKEN_FORBIDDEN`. If an existing route accepted them, opt in:

```env
AUTH_SERVICE_ALLOW_MACHINE_TOKENS=true
```

Prefer a separate machine-facing controller over enabling them globally.

## Audience

Set `AUTH_SERVICE_AUDIENCE` to the public URL of your API (the RFC 8707 resource
the frontend sends). Without it, the legacy `client_id` audience fallback is
kept, but auth-service access tokens are minted for a resource URL.

## New context fields

`request` / `socket` now also receive `plan`, `sid`, `clientId`, `scopes`,
`isMachine`, `auth` and `authToken`. Existing fields are unchanged. `authToken`
is the raw bearer token: never log it.

## Admin roles

`OidcSocketAdminMiddleware` now accepts any role listed in `adminRoles`
(`OIDC_ADMIN_ROLES` / `AUTH_SERVICE_ADMIN_ROLES`). The default remains
`["admin"]`.

## New dependencies and Node version

The package now depends on `@circle-rd/auth-ai` and `zod`, and requires Node 22+
and `ioserver` 2.2.1+ (2.3.0+ since 0.3.1).

## Generic providers

Existing deployments that verified another issuer with
`AUTH_SERVICE_URL` + `AUTH_SERVICE_APP_SLUG` can either keep that shape (it is
still accepted) or move to the explicit generic provider:

```env
OIDC_PROVIDER=oidc
OIDC_ISSUER=https://issuer.example.com
OIDC_JWKS_URI=https://issuer.example.com/.well-known/jwks.json
OIDC_AUDIENCE=api://my-api
OIDC_CLIENT_ID=my-client
```

The explicit provider is recommended because it documents the contract and
supports claim-name overrides.
