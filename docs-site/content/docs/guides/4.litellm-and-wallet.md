# LiteLLM and the Credit Wallet

When an application has **LiteLLM support** enabled in auth-service, its
`allowedResources` contains the gateway URL and the auth-service URL, and the
`wallet:self:read` scope is granted. The frontend requests all audiences at
sign-in:

```ts
const params = new URLSearchParams({
  client_id: "my-app",
  response_type: "code",
  redirect_uri: "https://app.example.com/callback",
  scope: "openid profile email roles permissions features offline_access wallet:self:read",
  code_challenge: challenge,
  code_challenge_method: "S256",
});
params.append("resource", "https://api.example.com");
params.append("resource", "https://llm.example.com");
params.append("resource", "https://auth.example.com");
```

The backend then mints one short-lived token per audience from the stored refresh
token. Never send a token minted for one audience to another service.

## Read the wallet before an expensive call

```ts
import { createWalletClient } from "ioserver-oidc";

class ChatController extends BaseController {
  async chat(request: any, reply: any) {
    const wallet = createWalletClient({
      authServiceUrl: config.authServiceUrl,
      token: request.authToken, // minted for the auth-service audience
    });

    const account = await wallet.getAccount();
    if (!account.canSpend) {
      return reply.code(402).send({
        code: "INSUFFICIENT_CREDIT",
        topupUrl: wallet.topupUrl(),
      });
    }

    const gateway = createRequestGatewayClient(request, config);
    const answer = await gateway.postJson("/v1/chat/completions", {
      model: "gpt-4o-mini",
      messages: [{ role: "user", content: "Hello" }],
      metadata: { session_id: request.sessionId },
    });
    reply.send(answer);
  }
}
```

`canSpend` is authoritative: it is true for an unlimited account or a strictly
positive balance. Do not recompute it from `balance`.

## Handle gateway refusals

| Status | Code     | Action                                                |
| ------ | -------- | ----------------------------------------------------- |
| `402`  | `GW_001` | Tell the user, link to `wallet.topupUrl()`, do not retry |
| `429`  | `GW_002` | Retry with a delay                                     |
| `401`  | `GW_003` | Mint a fresh gateway token and retry once              |
| `403`  | `GW_003` | Ask the operator to grant the model to the plan        |
| `503`  | `GW_004` | Retry shortly; the wallet or gateway is unavailable    |

`isInsufficientCredit(error)` is re-exported.

## Attribute spend to a session

Pass `metadata.session_id` in the gateway request. Then read the session cost
with `wallet.getSessionUsage(sessionId)`. The query is scoped to the calling
application (`azp`), so two applications cannot read each other's session spend.

## What the application does not do

- It does not debit the wallet: the gateway bills after each call.
- It does not hold provider API keys.
- It does not compute prices: auth-service applies the exchange rate and margin.
